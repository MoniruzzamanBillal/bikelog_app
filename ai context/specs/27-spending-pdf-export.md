# 27: Spending PDF Export

Status: ✅ Complete

## Goal

Add an "Export PDF" action to the Spending screen's Month/Year/Lifetime tabs that generates a PDF report of that period's spending — total, category breakdown, and the full list of individual fuel/maintenance line items (date, category, description, amount, vendor, remarks) — and hands it to the OS share sheet so the rider can save or send it. This is the mobile port of the already-shipped web client feature (`bikelog_client-web-`'s own spec 21, `context/specs/21-spending-pdf-export.md`, ✅ Complete), explicitly deferred there until this app was ready for it — same feature, same backend data source, platform-appropriate generation/delivery mechanism.

## Design

### Where the data comes from

`bikelog_server` spec 23 ("Spending Details Export Endpoint", ✅ Complete, live) added `GET /bikes/:bikeId/spending-summary/details?period=month|year|lifetime&targetMonth=YYYY-MM&targetYear=YYYY`, returning:

```ts
export type TSpendingRecordSource = "fuel" | "maintenance";

export type TSpendingRecord = {
  date: string;
  category: string;
  description: string;
  amount: number;
  vendor: string | null;
  remarks: string | null;
  source: TSpendingRecordSource;
};

export type TSpendingDetails = {
  period: "month" | "year" | "lifetime";
  targetMonth?: string;
  targetYear?: string;
  totalSpending: number;
  categoryBreakdown: TCategoryBreakdown[]; // already declared in types/spending.types.ts
  records: TSpendingRecord[]; // ascending by date
};
```

This is the exact same endpoint and response shape `bikelog_client-web-`'s spec 21 already consumes and has verified live — no backend work, no contract-discovery risk here. Cross-check against `../bikelog_server/src/app/modules/spending/spending.interface.ts` directly if anything below looks off, per this project's own "verify against backend source" rule — don't take this spec's copy of the shape as more authoritative than the source.

### Where PDF generation happens: on-device, via `expo-print`, not a server change

Same reasoning as the web client's spec 21: keep the backend endpoint a plain JSON aggregation, generate the document entirely client-side. Concretely, that means:

- **`expo-print`**'s `Print.printToFileAsync({ html })` — takes an HTML string and renders it through the platform's native print pipeline (iOS: `UIPrintInteractionController`; Android: `PrintManager`), returning `{ uri, numberOfPages }` for a real PDF file written into the app's cache directory. No native module linking beyond `expo install`, no manual font embedding.
- **This sidesteps a real bug the web client actually hit and had to work around.** `bikelog_client-web-`'s spec 21 tried `jsPDF` first, which manually embeds/subsets font glyphs into the PDF byte-by-byte — its built-in fonts are Latin-1/WinAnsi only, so the `৳` currency symbol rendered as mojibake, and embedding a Bengali-script TTF to fix it made things *worse* (broke jsPDF's font parser badly enough to drop plain Latin text too, confirmed via an isolated test outside the browser) — the web client shipped with an ASCII `"Tk"` fallback instead of `৳` in the PDF specifically, documented in its own spec 21 and `progress-tracker.md`. **`expo-print` does not have this problem the same way**, because it isn't manually embedding font glyphs at all — it hands a plain HTML/CSS string to the OS's own print/rendering pipeline, the same rendering path this app's own screens already use to display `৳` correctly today (system fonts already cover Bengali Unicode, confirmed by every existing `৳{amount.toFixed(2)}` on the Spending screen right now). So the plan below keeps `৳`, not `"Tk"` — **but this is an expectation, not yet a confirmed fact for this specific pipeline**, so the first Verify item below is an explicit visual on-device check of the `৳` symbol specifically, with the exact same ASCII-fallback escape hatch documented as a fallback if it turns out the OS webview substitutes a tofu/missing-glyph box for it on the test device.

### Filename control

`printToFileAsync`'s returned `uri` has an OS-generated random filename inside the cache directory — there's no parameter to control it directly. Match the web client's exact filename convention (`spending-<period>-<targetMonth|targetYear|"lifetime">.pdf`, e.g. `spending-month-2026-08.pdf`) by copying the generated file to a new path with the desired name via `expo-file-system`'s `FileSystem.copyAsync({ from: uri, to: \`${FileSystem.cacheDirectory}${filename}\` })` before handing it to the share sheet — the share sheet reads the file's name from the path it's given, so this is what actually controls what the user sees offered to save/send.

### Delivery: OS share sheet, not a "download"

Mobile has no browser-style direct-to-Downloads save. The idiomatic Expo pattern is `expo-sharing`'s `Sharing.shareAsync(uri, { mimeType: "application/pdf", dialogTitle: "Export Spending Report", UTI: "com.adobe.pdf" })`, guarded by `Sharing.isAvailableAsync()` first (returns `false` on some Android emulators/web — if unavailable, surface a `Toast.show({ type: "error", ... })` explaining the report was generated but can't be shared on this device, rather than silently no-op'ing). This opens the native share sheet, where "Save to Files"/"Save to device" is one of the options alongside any installed app capable of receiving a PDF (WhatsApp, email, Drive, etc.) — that's the mobile equivalent of the web client's browser download, not a gap to work around.

### UI placement

`components/main/Spending/Spending.tsx` has three tab components — `MonthTab`, `YearTab`, `LifetimeTab` — each already rendering its own period picker (`MonthStepper`/`YearStepper`/nothing) above a `SpendingSummaryView`. Unlike the web client, there's no `"trend"` tab to hide this button from — spec 25 already removed trend charts from this app entirely, so the button is simply present on all three existing tabs, no conditional-hide logic needed at all.

Add the button directly below each tab's period picker (below `MonthStepper`/`YearStepper`; at the top of `LifetimeTab`'s content, since it has no picker), above the `SectionLoading`/`SpendingSummaryView`/`EmptyState` branch. Use `react-native-paper`'s `Button` — this app's only button component (see `BikeDocument.tsx`'s `<Button mode="contained">Add Document</Button>` for the established idiom) — with `mode="outlined"` (visually secondary to whatever primary action already exists on-screen, there isn't one here so `outlined` vs `contained` is a minor call either way), `icon="tray-arrow-down"` (or `"file-pdf-box"` — `MaterialCommunityIcons`, already the app's only icon set via `@expo/vector-icons`; first use of either name in this app, confirm the exact glyph renders as expected before locking it in), and Paper's own built-in `loading`/`disabled` props while exporting (no separate spinner component needed — unlike the web client's manual `Loader2`+`animate-spin`, Paper's `Button` already has a loading-state built in that this app hasn't needed to reach for yet but is documented Paper API).

### Button states

- Default: icon + "Export PDF" label.
- While fetching `/spending-summary/details` and while `expo-print`/`expo-sharing` are running: `loading` + `disabled` on the `Button`, label reads "Exporting...".
- On fetch failure: re-enable, `Toast.show({ type: "error", text1: "Export failed", text2: <backend message>, position: "top" })` — matching this app's established error convention (see `BikeDocumentFormModal.tsx`'s `Toast.show` calls), not a fabricated message.
- On `expo-print`/`expo-sharing` failure (distinct from a network failure — the fetch can succeed and PDF generation/sharing can still fail on-device): same `Toast.show` pattern, a generic "Couldn't generate the PDF" message since there's no backend `message` field for this failure class.
- On success: share sheet opens; button returns to default state once `Sharing.shareAsync` resolves (which happens whether the user actually shares/saves or dismisses the sheet — that's expected `expo-sharing` behavior, not a bug to work around).

### PDF content and layout (HTML string, rendered by `expo-print`)

Build a plain HTML string with an inline `<style>` block (no external stylesheet, no network fetch inside the generated document). Structure, top to bottom, mirroring the web client's spec 21 exactly for feature parity:

1. **Header**: "Spending Report" title, a subtitle line with the human-readable period (e.g. "August 2026" for month — derive via `date-fns`'s `format(parse(targetMonth, "yyyy-MM", new Date()), "MMMM yyyy")`, matching the月/year-label pattern already used elsewhere in this file; the raw `targetYear` string for year; the literal "Lifetime" string), and a small "Generated <timestamp>" line (`format(new Date(), "d MMM yyyy, h:mm a")`).
2. **Summary**: "Total Spending: ৳{totalSpending.toFixed(2)}" — `.toFixed(2)`, matching this screen's own existing convention (`SpendingSummaryView.tsx` uses `.toFixed(2)` throughout, **not** `.toLocaleString()` like the web client — don't copy the web client's formatting call verbatim, this app has its own established one).
3. **Category breakdown table**: plain HTML `<table>`, columns `Category | Total (৳)`, one row per `categoryBreakdown` entry.
4. **Line-item table**: plain HTML `<table>`, columns `Date | Category | Description | Amount (৳) | Vendor | Remarks`. Format `date` via `date-fns`'s `format(new Date(record.date), "d MMM yyyy")`. Render `vendor`/`remarks` as `"-"` when `null` — never a blank cell, never the literal string `"null"`. Don't re-sort — the API already returns `records` ascending by date.

If `records.length === 0`, still generate and share a real PDF (header + "Total Spending: ৳0.00" + "No spending records for this period." in place of the line-item table) — don't silently no-op the button tap when a period genuinely has nothing logged.
