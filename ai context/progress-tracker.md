All 13 specs are code/type/lint-verified against the documented contract (`dummy-data.md`, the Postman collection, and — increasingly, as of the specs 05+ and the 09–13 review pass — the backend's actual source read directly) and cross-checked against the already-shipped web client, but no real request/response round-trip or on-screen render has been observed firsthand for anything in this app. This is the single highest-priority thing to do once a device/simulator + running backend are available — start with swipe gestures, modal layout, tab bar icons, the borderless-underline `TextInput` styling, and the reminders/maintenance-log screens specifically (the one place a real bug was already found by static review; there could be others static review can't catch).
- **The already-shipped web client (`bikelog_client-web-/`) has the same reminders-banner bug this session fixed in the mobile app** — `components/(main)/MaintenanceLog/RemindersBanner.tsx` reads `r.maintenanceType.name` assuming a populated object, but the backend never populates it (confirmed directly in `bikelog_server/src/app/modules/maintenanceLog/maintenanceLog.service.ts`). This is a separate, independently-tracked project — per the cross-project rule, this was not fixed here, only flagged. Worth surfacing to whoever maintains that project; the fix is the same shape as the one applied here (resolve the ObjectId against the fetched maintenance-types list instead of assuming population).
- **`.expo/types/router.d.ts` needs a real `expo start` run to regenerate accurately.** It was deleted (not hand-edited) after specs 05/06 found it stale; it's gitignored and will repopulate correctly the next time the dev server actually runs. Until then, `tsc` runs without it (confirmed clean) rather than against a misleading snapshot.
- **Picker's visual fit with Paper is unconfirmed.** Spec 02 implemented `SelectPickerField` per its documented default choice; spec 13 (bike accessories) is its first real usage in an actual form. Neither could be visually verified against Paper's `TextInput` styling — no device/simulator in this environment. If it visually clashes when actually run, `SelectPickerField.tsx` needs to be swapped for a Paper-`Menu`-based fallback.
- **Final `COLORS` values are a first pass, not a design decision** — spec 01 picked concrete hex values (`primary: "#2196F3"` etc.) to unblock every later spec that needs `COLORS` to exist; revisit the actual palette whenever real screens make it visually evaluable, per spec 01's own note that this is "purely aesthetic, not urgent."
- **`DatePickerField`'s native picker rendering is unconfirmed** (spec 14) — same category of gap as the Picker/Menu decision above: `@react-native-community/datetimepicker` is a real native module (Android dialog / iOS spinner), and neither its visual fit against the app's borderless-underline field convention nor its actual on-device behavior (dialog dismiss timing, spinner interaction) has ever been exercised — no simulator/device in this environment for any spec, including this one.
- **Spec 16's swipe-Edit fix is a well-founded hypothesis, not a confirmed root cause.** The `TouchableOpacity`-from-`react-native-gesture-handler` swap is the standard fix for this exact class of symptom, but static review couldn't fully explain why Delete worked while Edit didn't (both used the identical touchable before the fix). The user has not yet confirmed whether tapping a card *directly* (no swipe) ever failed too — if it did, the real bug is downstream of the tap (Modal/Portal rendering) and this fix alone won't resolve it. Ask the user to confirm this on their next device session; if Edit is still broken after this fix, that diagnostic is the next step, not another gesture-related tweak.
- **`SelectPickerField`'s height fix (40→50, spec 16) and `MaintenanceLogFormModal`'s prefill-race fix are code-verified only** — no simulator/device available in this environment to confirm the text no longer clips or that the prefilled catalog picker now shows correctly once loaded.
- **Bike accessory `price` (spec 15) has never been exercised against a live backend** — implemented purely by reading `../bikelog_server`'s source, since that backend hasn't been deployed with the field yet. Submitting a price will 400 against whatever backend is actually live until the deployment happens. Confirm the deployed backend accepts/returns `price` before relying on this in real use; also note (per spec 15's own scope) that accessory `price` is deliberately **not** wired into the spending-summary totals on either side.
